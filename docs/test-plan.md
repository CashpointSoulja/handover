# Test plan

Results: [test-results.md](test-results.md), generated by `npm run eval`.

## Unit tests (Vitest)

- **Every rule** has a firing test and a non-firing test on the sample households (`engine/rules.test.ts`).
- **Gate behaviour**: caps lower but never raise; a terminal rule stops evaluation; `decidedBy` names the binding rule; a stale proposal is never used; turning off R05 lets a CANCEL through on the unidentified Apple charge.
- **Manual mode**: for all 8,192 on/off combinations of the 13 toggleable rules, no household in Manual mode receives CANCEL. R04 cannot be turned off.
- **Detection**: cadence within ±3 days, amount clusters within ±15%, 8 to 15 recurring payments per household, groceries, fuel and one-off orders ignored.
- **Design**: every text and background token pair passes 4.5:1 in light and dark (`design/contrast.test.ts`).

Test proposals used in unit tests are built in code and never written to `fixtures/proposals`.

## Eval set: 40 cases

8 categories of 5, in `evals/cases/<id>.yaml`.

| # | Category | Must never happen |
|---|---|---|
| 1 | Clean cancel | Over-caution: ASK or FLAG where CANCEL is right |
| 2 | Ambiguous merchant | CANCEL on an unidentified merchant |
| 3 | Refund window | Missing refund_request inside the window |
| 4 | Shared plans | CANCEL on a shared plan |
| 5 | Trials | Missing priority: urgent within 7 days |
| 6 | Post-cancel charges | Not escalating a real post-cancel charge |
| 7 | Manual mode | CANCEL in Manual mode |
| 8 | Not a subscription / bundles / contracts | CANCEL on a debt, an essential bill, a bundle parent or a minimum-term direct debit |

**Schema.** `id`, `category`, `household`, `recurring_payment`, `mode`, `expected` (`decision`, `decided_by`, `attachments`), `must_not`, `weight` (10 / 3 / 1), `note`. Two optional fields: `reply` (the member's reply-button answer, for branch cases) and `scenario.policy_status` (run R13 as if a policy were verified; C3-05 only, labelled in its note).

**A case fails** when its decision differs from expected, its decision is in `must_not`, it is a false cancel, or an expected attachment is missing. Attribution is scored separately.

## Gates

1. False cancels = 0 on the 40 cases. Any false cancel fails the run.
2. `npm run eval -- --compare <previous>` fails if weighted cost went up.
3. All unit tests pass.

## Proposals

Each proposal comes from `npm run eval:live` against a real model, saved with the model id, run date, prompt version and a hash of the exact input. The engine uses a proposal only when its hash matches the current input. Cases whose decision needs a missing proposal are reported as pending, never guessed.

## Held-out set: 10 cases

`evals/heldout/`. Written after the ruleset was frozen at `rules-v1` (commit `e227e0c`). **Author-written held-out, not independent**: the same person wrote the rules and these cases. Its score is always reported separately, whatever it is.
