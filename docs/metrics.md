# Metrics

Every score here is an eval score on this case set, not a member outcome and not production accuracy. If the proposals behind a run are chat-recorded rather than live API runs, [test-results.md](test-results.md) says so. Current numbers are in [test-results.md](test-results.md), which is generated by `npm run eval` and never edited by hand.

| Metric | Definition | Direction | In production it would mean |
|---|---|---|---|
| **False cancels** (hard gate) | Cases where the decision is CANCEL and the expected decision is not. Any false cancel fails the whole run, whatever the other numbers say. | Must be 0 | Members who lost something they wanted. The number that ends trust, so it gates every release. |
| **Weighted cost** | Sum of `weight` over failed cases: 10 = false cancel, 3 = missed money (a refund window, an urgent trial, a post-cancel charge), 1 = an unnecessary ask. | Lower is better; a rule change must not raise it | The cost of the system's mistakes, priced the way a member feels them. `--compare` fails a change that raises it. |
| **Decision accuracy** | % of scored cases whose decision matches the expected one. | Higher is better | How often the member gets the right kind of message. |
| **Attribution accuracy** | % of scored cases where `decidedBy` matches the expected rule or `llm`. | Higher is better | Whether the system is right for the right reason. A correct answer from the wrong rule is a latent bug that the next config change will expose. |
| **Asks per household** | Average number of ASK decisions per household on the sample data. | Reported beside accuracy, not maximised | Nag cost. Every question spends member attention; safety bought with endless questions is not safety members keep using. |

## Why the scoring is asymmetric

Cancelling something a member wanted costs more trust than missing a saving. So a false cancel weighs ten times an unnecessary ask, and the false-cancel count is a gate, not a term in an average.

## Guarding against an engine that never acts

The clean-cancel category (5 cases) expects CANCEL. An engine that never cancels fails all five, so it cannot score perfectly; the unit tests check this.

## Pending

A case is pending when its decision needs a recorded proposal that does not exist yet. Pending cases are not scored and do not count towards accuracy or cost. The gate reads "pending" rather than "pass" until every case is scored.
